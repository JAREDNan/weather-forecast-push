## 一、部署方案对比与推荐

| 维度 | A. PythonAnywhere（蓝本方案） | B. 国内轻量云服务器 | C. 本机长期运行（不推荐） | **D. GitHub Actions（新增，推荐）** |
|---|---|---|---|---|
| **成本** | 免费版受限；付费 $5/月 | ¥50-100/年（学生优惠） | 免费但需 7×24 开机 | **完全免费** |
| **定时任务** | ⚠️ 免费版受限 | ✅ systemd timer | ✅ 本机计划任务 | ✅ Actions cron（UTC，已换算北京时间） |
| **出站网络** | ⚠️ 白名单受限 | ✅ 无限制 | ✅ 无限制 | ✅ 无限制（微软云节点） |
| **访问国内气象站** | ⚠️ 境外延迟高 | ✅ 国内节点 | ✅ 本机网络 | ✅ 实测可达（weather.com.cn/nmc.cn） |
| **访问微信接口** | ⚠️ 境外不稳定 | ✅ 稳定 | ✅ 本机网络 | ⚠️ 仅企业微信 webhook 可用（公众号 API 白名单无法固定 IP） |
| **密钥管理** | .env | .env | .env | **仓库 Secrets 注入环境变量**（更安全） |
| **可靠性** | 中 | 高 | 极低 | **高**（GitHub 托管 SLA） |

**推荐结论（2026-10-21 更新）：**

1. **首选：GitHub Actions 免服务器（方案 D）**——完全免费、无需任何服务器、密钥走
   Secrets 更安全。**前提**：当前推送路线为企业微信群机器人（webhook 无需固定 IP），
   公众号侧保持「人工手动群发推送包」辅助，两条通道云端均可运转。
2. **若未来公众号完成认证**、需走 API 群发（要求 access_token 的 IP 白名单）：
   再切回方案 B 轻量云服务器（独享公网 IP 是刚需），GitHub Actions 无法满足固定 IP。
3. 方案 C 仅用于本地开发调试。

## 二、部署到轻量云服务器（systemd 方案，推荐）

### 2.1 服务器准备

```bash
# 以 Ubuntu 22.04/24.04 为例
apt update && apt install -y python3-venv python3-pip git

# 上传项目（或用 git 拉取，注意 .env 不入库，需手动放入）
mkdir -p /opt/weather
# scp/rsync 上传 G:\气象预报平台\ 下除 venv/data 外的内容
```

### 2.2 环境与依赖

```bash
cd /opt/weather
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
# 若启用微信推送（已选定订阅号路线）：
pip install -r requirements-wechat.txt

# 验证
python main.py --selftest && python main.py --collect
```

### 2.3 配置密钥

```bash
cp .env.example .env
nano .env   # 填入 WECHAT_APP_ID / WECHAT_APP_SECRET / WECHAT_PUSH_CHANNEL=subscription 等
chmod 600 .env   # 仅属主可读写
```

### 2.4 systemd 服务（每日任务）

创建 `/etc/systemd/system/weather-daily.service`：

```ini
[Unit]
Description=Weather Forecast Daily Push
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
WorkingDirectory=/opt/weather
ExecStart=/opt/weather/venv/bin/python /opt/weather/main.py --push
Environment=TZ=Asia/Shanghai
# 密钥文件权限
UMask=077
```

创建 `/etc/systemd/system/weather-daily.timer`（07:30 推送，采集在 `--push` 内部自动提前）：

```ini
[Unit]
Description=Weather Daily Timer

[Timer]
OnCalendar=*-*-* 07:30:00
Persistent=true
RandomizedDelaySec=120

[Install]
WantedBy=timers.target
```

启动：

```bash
systemctl daemon-reload
systemctl enable --now weather-daily.timer
systemctl list-timers weather-daily.timer   # 查看下次执行时间
journalctl -u weather-daily.service -f      # 查看运行日志
```

> 时区说明：北京时间 07:30 = UTC 前一日 23:30（UTC+8）。**建议直接把服务器时区设为
> Asia/Shanghai（`timedatectl set-timezone Asia/Shanghai`）**，`OnCalendar=*-*-* 07:30:00`
> 即按北京时间的 07:30 触发，避免 UTC/北京时间换算错误。

### 2.5 失败告警（避免静默失败）

`.env` 中配置 `ALERT_WECOM_WEBHOOK`（企业微信群机器人）或 `ALERT_SERVERCHAN_KEY`（Server酱），任务失败时自动推送告警。全部留空则仅写日志 + `logs/scheduler.log` 记录连续失败次数。

### 2.6 微信 IP 白名单

登录微信公众平台 → 开发 → 基本配置 → IP 白名单，加入服务器公网 IP。否则 access_token 返回 `errcode 40164`。

## 三、首次上线流程（严格顺序，防止误推）

```bash
# 第 1 步：离线自检
python main.py --selftest

# 第 2 步：真实采集一次，核对数据
python main.py --collect

# 第 3 步：干跑生成文案，人工审阅 logs/dryrun_*.md
python main.py --dry-run

# 第 4 步：仅发给自己预览（不消耗群发额度）—— 提示词 §6.3 强制要求
python main.py --push --preview-openid <你的微信openid>

# 第 5 步：确认排版无误后，正式群发一次
python main.py --push

# 第 6 步：启动每日定时
python main.py --serve        # 前台运行（开发）
# 或 systemd timer（生产，见 2.4）
```

> ⚠️ 订阅号每天仅 1 次群发额度（0 点重置）。若当天已手动群发，`--push` 会失败（errcode 45009 类）。正式上线后请勿在公众号后台手动群发同日消息。

## 四、日常运维

### 4.1 每日检查（可选，系统失败会自动告警）

```bash
python main.py --status        # 数据库行数、最近采集时间、配置状态
```

### 4.2 日志

| 位置 | 内容 |
|---|---|
| `logs/scheduler.log` | 调度与任务运行日志（含连续失败计数） |
| `logs/dryrun_*.md` | 干跑文案（人工审阅用） |
| `data/raw/` | 原始报文归档（按日期，只增不改） |
| `data/db/weather.sqlite` | 结构化数据（每日累积，供未来建模） |

### 4.3 数据维护

- 原始报文按日期归档，`config.ini` 中 `raw_retention_days=365` 控制保留天数（需人工清理，系统不做自动删除以避免误删）。
- `weather.sqlite` 随每日采集自动累积，建议每月备份一次：
  ```bash
  cp data/db/weather.sqlite backups/weather_$(date +%Y%m%d).sqlite
  ```

### 4.4 常见故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| access_token 40164 | IP 不在白名单 | 公众号后台加服务器 IP |
| 群发失败 45009 | 当天群发额度已用完 | 等待次日 0 点重置；检查是否手动群发过 |
| 采集失败但推送成功 | 官方源瞬时故障 | 系统自动降级缓存数据，文案会标注「缓存 + 数据更新时间」 |
| 文案无生活指数 | 和风天气未配置 | 官方源已有指数，属降级正常状态 |
| 连续失败无告警 | ALERT_* 未配置 | 配置告警渠道；检查 logs/scheduler.log |

### 4.5 升级与回滚

- 代码改动前备份：`git commit`（建议项目纳入 git，`.env`/`data/`/`venv` 已 gitignore）。
- 改动后先 `--selftest` + `--dry-run` 验证，再重新加载 systemd：`systemctl restart weather-daily.timer`（timer 无状态，直接生效）。
### 4.6 云端（GitHub Actions）运维

| 操作 | 方法 |
|---|---|
| 查看运行结果 | GitHub 仓库 → Actions → 「每日天气推送」→ 点某次运行看各步骤日志 |
| 手动触发一次 | Actions → 该工作流 → **Run workflow**（不需等 cron） |
| 下载公众号推送包 | 该次运行的 Artifacts 区 → `gzh-pack-<run号>.zip`（保留 7 天） |
| 查看推送是否成功 | 「推送企业微信群机器人」步骤日志：`errcode=0` 即成功 |
| 修改推送时间 | 改 `.github/workflows/daily-push.yml` 的 cron（UTC，北京时间需 -8h） |
| 更新 Secrets | 仓库 Settings → Secrets and variables → Actions → Update |
| 失败排查 | Actions 日志 + `logs/scheduler.log`（会随 Artifacts 上传） |

**云端故障排查补充：**

| 现象 | 可能原因 | 处理 |
|---|---|---|
| Actions 中 --push 步骤失败但无发送 | Secrets 未配置或渠道为 dryrun | 配置 `WECHAT_PUSH_CHANNEL` / `WECOM_WEBHOOK_URL` Secrets |
| 采集失败（Actions 环境） | 官方源瞬时抖动 | 系统自动重试 2 次 + 熔断退避；下次运行自动恢复 |
| 想停用云端定时 | 仓库 Settings → Actions → 禁用该工作流（或删除 yml） | — |
